**The column count a host asked for was inert in a browser.** `<SearchResultsPane columns>` / `<SearchPage resultsColumns>` emitted a real sheet — a fixed `repeat(N, minmax(0, 1fr))` rule, or a base rung plus `@container` rungs for a map — and hung it on a class on the results grid. The pane also wrote `grid-template-columns: repeat(auto-fill, minmax(260px, 1fr))` as an INLINE style on that same node, and an inline declaration beats a stylesheet at any specificity. A stand set `{ phone: 1, tablet: 2 }` and measured pure auto-fill: two columns at 759px, one at 448, two at 900, three at 1199. Every unit test on the emitted CSS string stayed green, because none of them read the rendered node.

The pane no longer writes the auto-fill default when the host has an opinion: a fixed count is written INLINE (one number, no cascade to run) and a map leaves the property unset inline so its own rungs are the only ones in play. Because there is then nothing inline to inherit from, the map's sheet always states its base rung — the `phone` count, or the auto-fill default when `phone` is left out, so "a key left out inherits the rung below it" still holds. `data-columns` and the class are unchanged, and the tests now read `style.gridTemplateColumns` off the rendered grid rather than the string the generator returned. `RESULTS_AUTO_FILL_COLUMNS` is exported for a host that wants to state the same default itself.

**`<SearchPage railFrom>` — where the filter rail takes over from the sheet.** The changeover was `useDialogSurface()`, i.e. the token `tablet` edge, because that is where a DIALOG stops being a bottom sheet. For this layout that is often the wrong number: at 768px the 280px rail leaves the results a 470px column, one card wide, and worse than the sheet it replaced. `railFrom={1024}` moves the threshold to where a deployment's cards actually fit beside the rail; below it the filters are the sheet. It is read live off the viewport through one `matchMedia` handle in a `useSyncExternalStore` — the shape `useDialogSurface` uses — so the first client render already has the answer and rotating a tablet across the threshold swaps the surface without a reload.

**`<SearchPage filtersLayout>` is a real prop.** Its documentation called itself a test override; it is the PINNED answer, for a page rendered inside a phone-width container that is not the viewport (a preview frame, an embedded panel, a split view) or a surface that is a column by product decision at every width. It still wins over `railFrom`.
